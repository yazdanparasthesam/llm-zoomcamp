# Azure deployment — Azure Container Apps + Groq

TripPilot's Azure deployment path follows **Step 11 in the [main README](../README.md)**: Azure Container Apps hosts the application, and Groq provides the model API. The implementation uses **Azure CLI and Bicep**, with a credit-protected subscription and a separately verified Groq Free organization.

> **Directory distinction:** the `.tf` files in this directory still describe the optional **GCP Cloud Run** deployment. They have not been converted to Azure. Do not run `terraform init` or `terraform apply` here expecting an Azure deployment. The Azure implementation is in [`../azure/`](../azure/).

Visitors who only want to use TripPilot can open the [Streamlit live demo](https://tripilot-chatbot.streamlit.app/) instead; using that demo does not require an Azure subscription.

## Azure deployment architecture

| Component | Configuration |
|---|---|
| Resource group | A dedicated group for the TripPilot cloud demo |
| Container Registry | One Standard registry; administrative account disabled |
| Image authentication | User-assigned managed identity with `AcrPull` scoped to the registry |
| Container Apps environment | Consumption-only; no Log Analytics workspace requested |
| Container App | 0.5 vCPU, 1 GiB memory, zero to one replica, single active revision |
| Public access | HTTPS ingress to Streamlit on port 8501 |
| Health probes | Startup, readiness, and liveness checks against `/healthz` |
| Model provider | Groq; model names are configured explicitly and checked for account access |
| API-key handling | A secure Bicep parameter and a Container Apps secret reference |
| Cloud telemetry | Ephemeral SQLite and JSONL files inside the container |

The lean Azure deployment does not provision PostgreSQL, Elasticsearch, or Grafana. The complete local Compose/Kind stack remains a separate deployment path. Container-local telemetry can reset after restarts, new revisions, or scale-to-zero; this configuration is not a durable database or a high-availability deployment.

## Prerequisites and spending controls

- An **Enabled** Azure subscription with an eligible trial/student credit offer, available credit, a future expiry date, and **spending limit On**.
- Permissions to create the dedicated resources and assign the registry-scoped image-pull role.
- Azure CLI, its Container Apps extension, Bicep, Docker, and Python 3.
- A Groq organization whose **Free plan**, model access, and quota have been checked separately.

Do not upgrade Azure to Pay-As-You-Go, remove its spending limit, buy Marketplace/support products, or upgrade Groq plans to bypass a failed check. Azure credits do not pay Groq invoices. Registry and compute usage can consume credits when an offer's free allowances do not cover them.

The subscription helper verifies **Enabled + spending limit On**; it does not verify remaining credit or expiry. Check those in the Azure portal. Spending limits also do not cover every possible external charge.

## Execution order

Use the commands in the linked Azure guides, in this order:

1. **Account readiness:** activate an eligible credit offer, sign in, and check the intended subscription — [`azure/START-HERE.md`](../azure/START-HERE.md).
2. **Local validation:** build the application image using the pinned dependencies and verify Groq authentication and model access without displaying the key.
3. **Infrastructure:** create the dedicated resource group, registry, managed identity, registry-scoped role, and Consumption-only environment.
4. **Image publication:** push the tested image and obtain its immutable digest.
5. **Application deployment:** deploy [`azure/containerapp.bicep`](../azure/containerapp.bicep) using the protected parameter file generated by [`azure/write_parameters.py`](../azure/write_parameters.py).
6. **Verification:** check revision readiness, the actual HTTPS URL, `/healthz`, a cited response, feedback, and the cloud app's own monitoring totals.
7. **Cleanup:** after use or review, export any records that must be retained and delete only the dedicated Azure resources, following the scoped cleanup instructions.

The [complete Azure + Groq guide](../azure/README-azure.md) provides the individually explained commands, model checks, secret handling, and cleanup procedure. Run application build and deployment commands from the **project root containing `app.py`**, not from this `terraform/` directory or the course-repository root.

## Secret and data handling

- Create the model API key in **Groq Console**, not Azure OpenAI.
- Never place a real key in Terraform files, Bicep source, Docker build arguments, Git, or public documentation.
- The generated `.azure/tripilot-parameters.json` is private local state, excluded from Git and Docker. Do not display or share it; remove it after deployment.
- A working Streamlit Community Cloud demo is not evidence that the Azure deployment has been completed.
- Keep Azure deployment claims tied to an actual verified Azure endpoint. Configuration files alone do not establish a live deployment.

## Optional GCP Terraform files

[`main.tf`](main.tf), [`variables.tf`](variables.tf), and [`outputs.tf`](outputs.tf) remain GCP-specific alternatives. They are not invoked by the Azure workflow and do not create Azure resources. Their presence does not require using or paying for GCP.
